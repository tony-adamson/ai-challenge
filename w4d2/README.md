# Исследователь — первый инструмент MCP

День 17: собственный MCP-сервер на Rust вокруг публичного GitHub Search API.
Агент получает описание инструмента от сервера, выбирает вызов через native tool
calling, получает результат и использует его для ответа со ссылками.
Основа — `w4d1`: сохранены чат, память, инструкции, инварианты и утверждение плана.

## Запуск

Требуется Rust 1.88 или новее. Первая сборка скачивает зависимости.
Команды выполняются из папки `w4d2`.

Каталог собственного MCP-сервера, без LLM-ключей и сетевого запроса к GitHub:

```bash
cargo run -- --github-tools
```

Реальный поиск через MCP и GitHub API, также без LLM-ключей:

```bash
cargo run -- --github-search 'full-text search language:Rust archived:false'
```

Приложение запускает собственный сервер дочерним процессом и общается с ним через
stdio. Для подключения другого MCP-клиента сервер можно запустить напрямую:

```bash
cargo run -- --github-mcp-server
```

В этом режиме stdout занят протоколом JSON-RPC. CLI-режимы не читают `.env`
и не создают данные чата. Ошибка поиска даёт ненулевой код завершения.

Веб-интерфейс с агентом:

```bash
cargo run
```

Открой `http://127.0.0.1:8799`. Для чата нужен ключ выбранного LLM-провайдера
в корневом `.env` (см. `../.env.example`) и модель с поддержкой function calling.
Данные этого дня хранятся отдельно в `w4d2/data/`.
В панели **Инструменты · MCP → Каталог GitHub MCP** видны имя, описание и схема
параметров собственного инструмента. Каталог Exa из прошлого дня тоже доступен;
агент вызывает только GitHub-инструмент.

## Инструмент и путь результата

`search_repositories` принимает два обязательных параметра:

| Параметр | Ограничения | Пример |
|---|---|---|
| `query` | Непустая строка до 256 символов, синтаксис поиска GitHub | `full-text search language:Rust archived:false` |
| `limit` | Целое число от 1 до 5 | `3` |

Сервер вызывает `GET https://api.github.com/search/repositories`. Результат:
название, ссылка, описание, язык, звёзды, дата последнего push, признак архива;
также возвращаются `total_count` и `incomplete_results`.
Это метаданные поиска: README и код не читаются, звёзды не доказывают качество.
Используется публичный доступ без GitHub-токена, с ограничениями частоты запросов.
[Документация GitHub Search API](https://docs.github.com/en/rest/search/search#search-repositories).

1. На этапе **Выполнение**, после утверждения плана, приложение подключается к
   своему MCP-серверу и получает `tools/list`.
2. Схема передаётся модели в `tools`. Модель сама выбирает аргументы или отвечает
   без поиска, если он не нужен.
3. Приложение выполняет `tools/call`, возвращает данные модели сообщением `tool`
   с тем же `tool_call_id` и получает итоговый ответ.
4. В ленте появляется раскрываемая карточка с аргументами и фактическим
   результатом. Она сохраняется вместе с ответом и видна после перезагрузки.

Один ход допускает максимум один поиск. Финальная генерация и повтор ответа
после проверки инвариантов используют уже полученные данные, без нового поиска.
Ошибка инструмента возвращается с `isError: true`, а не как пустой успех.
На GitHub HTTP-запрос отведено 15 секунд, на MCP-вызов — 20 секунд;
ответ API ограничен 128 КиБ. Описания репозиториев считаются данными,
а не инструкциями для агента.

## Где смотреть код

- `src/github.rs`: собственный `ServerHandler`, регистрация инструмента,
  JSON Schema, проверка параметров, GitHub API и результат MCP.
- `src/mcp.rs`: запуск subprocess, соединение по stdio и CLI-клиент.
- `src/agent.rs`: каталог → native tool call → `tools/call` → результат модели.
- `src/main.rs`, `static/index.html`: каталог в UI, события и карточка вызова.

## Проверки

```bash
cargo test
cargo clippy --all-targets -- -D warnings -A clippy::too_many_arguments -A clippy::double_ended_iterator_last
cargo run -- --github-tools
cargo run -- --github-search 'full-text search language:Rust archived:false'
```

95 тестов прошли. MCP-тест соединяет настоящий клиент и сервер SDK через duplex,
а GitHub API заменён локальным HTTP fixture: проверяются каталог и схема,
аргументы запроса, результат, неизвестный инструмент, неверные параметры,
ошибка HTTP, некорректный JSON и превышение размера ответа. Отдельный тест
проверяет сохранение `tool_call_id`, результата и reasoning в сообщениях модели.
Clippy проходит с исключением двух унаследованных классов замечаний из `w4d1`.

Живой CLI-поиск через собственный MCP-сервер и GitHub проверен 23 сентября 2026:
получены три репозитория, `isError: false`. Это доказывает соединение и вызов
инструмента, но не самостоятельный выбор инструмента моделью.
Полный живой сценарий также проверен через Cerebras, модель `qwen-3.8-27b`:
план → утверждение в интерфейсе → выбор `search_repositories` моделью →
результат MCP → ответ агента. Названия, ссылки, звёзды и даты трёх репозиториев
в ответе совпали с фактическим результатом инструмента. Карточка вызова
сохранилась после перезагрузки страницы. Другие LLM-провайдеры в этом сценарии
не проверялись.

## Сценарий видео

1. Показать в `src/github.rs` регистрацию `search_repositories`, схему параметров
   и обработчик, который обращается к GitHub и возвращает результат MCP.
2. Запустить приложение и открыть каталог GitHub MCP в интерфейсе.
3. В новом чате написать: «Найди три публичных GitHub-проекта на Rust для
   полнотекстового поиска. Нужны ссылки, краткое описание, звёзды и дата последнего
   push. Ответ оформи нумерованным списком со ссылками Markdown, без таблиц.
   Качество кода не оцениваем. Сначала предложи короткий план».
4. Если агент уточняет требования — ответить. Утвердить план кнопкой; перейти
   к выполнению и написать: «Выполни поиск через GitHub MCP по утверждённому плану».
5. Показать карточку `search_repositories`, её аргументы и реальный результат,
   затем ответ агента со ссылками. Сопоставить названия и числа с карточкой.
6. Обновить страницу и проверить сохранённую карточку вызова.

Для задания важен шаг 5: один каталог или CLI-поиск без ответа агента
не демонстрирует использование результата моделью. Секреты из `.env` в видео
показывать не нужно.
