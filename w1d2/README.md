# w1d2 — контроль формата ответа

Один и тот же запрос отправляется с разным уровнем контроля, и рядом видно,
что меняется. Все ограничения выставляются в мастере перед отправкой,
ничего не зашито в код.

## Запуск

```bash
cp ../.env.example ../.env   # вписать реальный DEEPSEEK_API_KEY
cargo run
```

Где есть выбор — стрелки и Enter, где нужен ввод — ввод. Прошлое значение
достаётся клавишей Tab — и для запроса, и для списка полей.

Мастер спрашивает только то, что имеет смысл: у свободного формата не
спрашиваются поля, у markdown нет `json-mode`, у диалога нет ни формата, ни
числа прогонов — там ответ всегда JSON-обёртка со `status`. После ответа
можно повторить с теми же настройками, перенастроить или выйти.

## Соответствие заданию

| Требование дня | Реализация | Где видно в выводе |
|---|---|---|
| Явное описание формата ответа | системный промпт со списком полей; отдельно — `response_format: {"type":"json_object"}` на стороне API | промпт печатается целиком перед запросом |
| Ограничение на длину ответа | `max_tokens` в теле запроса + инструкция отвечать коротко | `max_tokens: 1500` |
| Условие завершения ответа | `stop: ["<END>"]` в запросе **и** инструкция закрыть ответ маркером; в диалоге — логическое условие через поле `status` | `stop: ["<END>"]`, `finish_reason: stop` |
| Сравнить ответы без ограничений и с ограничениями | оба запроса уходят за один прогон и печатаются друг под другом | секции `БЕЗ ОГРАНИЧЕНИЙ` и `С ОГРАНИЧЕНИЯМИ` |
| Разный уровень контроля через API | каждый рычаг включается независимо в мастере | сводка «что уходит в модель» |

Каждый рычаг сделан дважды — инструкцией в промпте и параметром API, потому
что порознь они работают хуже: без инструкции модель не знает, что маркер
надо написать, а без `stop` в запросе может его не написать. Формат и
`json-mode` разведены намеренно: первый живёт в промпте, второй в параметрах
запроса, и включаются они независимо.

## Что показывает вывод

Перед запросом печатается системный промпт целиком — видно, какие ограничения
в нём сидят и что запрос идёт по API, а не через веб-чат:

```
system-промпт, который уходит в API:
│ Ответ — ровно один JSON-объект с полями: сорт, вкус, страна.
│ Ровно эти поля на верхнем уровне: ни одного лишнего, ни одного пропущенного.
│ Уложись примерно в 1500 токенов: пиши коротко, без вводных фраз.
│ Закончив ответ, напиши <END> и сразу прекрати генерацию.
max_tokens: 1500 · stop: ["<END>"] · response_format: нет
```

Сначала тот же вопрос уходит **без единого ограничения** — приходит несколько
килобайт markdown с заголовками и эмодзи, машиной такое не разобрать. Потом
тот же вопрос уходит **с ограничениями**, `N` раз подряд.

Проверяется не текст, а структура. Заказанный набор полей сверяется с тем,
что пришло: не хватает поля или появилось лишнее — видно построчно.
Стабильность между прогонами проверяется отпечатком — отсортированным списком
путей до листьев с их типами. Значения в отпечаток не входят, поэтому
«Арабика» и «Робуста» дают одинаковый отпечаток, а потерянное поле или
сменившийся тип — разный. Длина массива считается содержанием, а
разнородность его элементов — структурой.

При числе прогонов больше пяти вывод компактный: первый ответ целиком,
остальные строкой с образцом первого заказанного поля.

```
   2/20  ✓  сорт: Арабика
   3/20  ✓  сорт: Гейша
  …
  20/20  ✓  сорт: Типика

── ИТОГ ────────────────────────────────────────────
✓ структура одинакова во всех 20 разобранных прогонах
✓ содержание при этом разное — фиксируется формат, а не текст
```

Это и есть ответ на вопрос «должен ли ответ быть одинаковым»: одинаков
формат, содержание живое.

Прогоны, которые не разобрались, в сравнение не попадают — иначе три
одинаковых ошибки парсинга выглядели бы как стабильный формат. Если
разобрать не удалось ничего, итог так и говорит.

## Диалоговый режим

Режим «Диалог» включает многоходовый сбор данных. Каждый ответ модели —
JSON-обёртка, по которой цикл понимает, продолжать или заканчивать:

```json
{"status": "asking", "question": "Какой у вас бюджет?", "result": null}
{"status": "done",   "question": null, "result": { … заказанные поля … }}
```

Пока `asking` — программа печатает вопрос и ждёт ответ человека. На `done`
диалог заканчивается и `result` проверяется по списку полей. Строгий формат
здесь не украшение: на поле `status` держится управление потоком. Это второе,
логическое условие завершения — в отличие от стоп-маркера, который обрывает
один ответ, оно решает, когда закончить разговор.

Спрашивает модель только то, чего не может знать сама — предпочтения, бюджет,
цель, доступные условия. Факты заполняет своими знаниями: на `расскажи про
авокадо` с полями `цвет определение витамины` вопросов не будет ни одного, а
на `помоги выбрать ноутбук` с полями `модель цена почему` — будут, и на выходе
получится конкретная рекомендация.

Число прогонов в этом режиме не спрашивается — диалог требует живых ответов и
автоматически не повторяется.

## Замеченная особенность reasoning-моделей

`deepseek-v4-flash` тратит `max_tokens` в том числе на внутреннее рассуждение.
При лимите 600 модель нередко израсходует весь бюджет на размышление и вернёт
пустой `content` с `finish_reason: length`. Поэтому рядом с каждым ответом
печатается `finish_reason` и число токенов, ушедших на рассуждение, а пустой
ответ объясняется явно:

```
✗ лимит в 600 токенов израсходован до начала ответа (600 ушло на рассуждение)
  — выбери лимит побольше
```

Дефолт поэтому 1500, а 600 в списке помечены как рискованные — они полезны
именно как демонстрация того, что лимит длины ломает ответ. Если лимит съел
ответ на первом прогоне, остальные прогоны серии отменяются: результат от
повтора не изменится, а запросы платные.

Запрос без ограничений `max_tokens` не передаёт вовсе — там работает потолок
провайдера, поэтому ответ приходит на несколько тысяч символов.

## Как устроено

| Файл | Ответственность |
|---|---|
| `src/main.rs` | Два прогона (без ограничений / с ограничениями), итоговый вердикт |
| `src/wizard.rs` | Пошаговый мастер настройки |
| `src/format.rs` | Сборка системного промпта из ограничений, отпечаток структуры, сверка полей |
| `src/llm.rs` | Запрос в формате OpenAI Chat Completions, `finish_reason` и токены рассуждения |
| `src/dialog.rs` | Цикл диалога с логическим условием завершения |
| `src/ui.rs` | Цвет, крутилка, разделители секций, цитирование ответов, шаги инициализации |
| `.cargo/config.toml` | `term.quiet` — служебные строки cargo не мешают выводу программы |

Провайдер по умолчанию — DeepSeek; `LLM_PROVIDER=openrouter` в корневом `.env`
переключает на OpenRouter, `LLM_MODEL` переопределяет модель.

HTTP-клиент создаётся один раз на запуск: внутри блокирующего клиента живёт
свой рантайм, и пересоздание на каждый запрос стоило бы нового TLS-рукопожатия
вместо keep-alive. Таймаут — 90 секунд на этап; `reqwest` применяет его
отдельно к отправке и к чтению тела, поэтому худшее ожидание одного вызова
вдвое больше. Причина сетевой ошибки называется словами (таймаут, отказ
соединения, нечитаемый ответ), а не общим сообщением.

Формат задаётся списком полей через пробел — `сорт вкус страна`, без синтаксиса
JSON. Порядок пользовательский: он же уходит в промпт и в колонки
markdown-таблицы. Проверяется набор полей верхнего уровня; вложенных структур
список не описывает.

## Тесты

```bash
cargo test
```

17 тестов на `format.rs` — без сети. Проверяют главный инвариант: разные
значения при одинаковой структуре дают равные отпечатки, а потеря поля, смена
типа, обломанный элемент внутри массива, рваная markdown-таблица и обрезка по
стоп-маркеру — разные.
