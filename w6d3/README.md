# w6d3 — RAG Lab: RAG целиком на локальной модели

День 28: RAG-пайплайн из недели 5 отвечает через локальную LLM. Приложение
RAG Lab — macOS-окно с шариком из w4d5: задаёшь вопрос, получаешь ответ,
источники `source · section · chunk_id`, дословные цитаты, проверенные кодом,
вердикт судьи и метрики скорости. Вкладка «Сравнение» гоняет 12 контрольных
вопросов на двух локальных моделях и сводит качество, скорость и стабильность.

Модели ответа: `mlx-community/Qwen3.5-9B-MLX-4bit` и
`mlx-community/gemma-4-e4b-it-4bit`. Облачной модели-ответчика нет.

## Что локально и что ходит в сеть

- **Индекс** — `../w5d1/index.db` (SQLite, чанки `strategy=structure`), только чтение.
- **Эмбеддинги** — `multilingual-e5-small` через fastembed, кэш `../w5d1/.fastembed_cache`.
  Поиск — косинус по всем чанкам в памяти процесса, ~10 мс на вопрос.
- **Генерация** — `mlx_lm.server` на `localhost:8080`, веса в `~/.cache/huggingface`.
- **Из пайплайна в сеть ходит только судья** DeepSeek (`deepseek-v4-flash`, ключ из корневого
  `.env`, как в w5d4). Без сети ответ всё равно показывается, а вердикт —
  «недоступен (нет сети)».
- Ещё окно, пока открыто, раз в 15 с шлёт HEAD-запрос на `api.deepseek.com` без
  ключа и данных — только для индикатора «онлайн/офлайн».

Сервер модели и бинарник запускаются с `HF_HUB_OFFLINE=1`: ни один из них
не обращается к Hugging Face, поэтому всё, кроме судьи, работает с выключенным Wi-Fi.

## Как устроено

- `src/main.rs` — RAG на Rust, продолжение w5d4: тот же шлюз порога 0.85,
  тот же `ANSWER_SYSTEM`, та же проверка цитат кодом и ровно один повтор, тот же
  `JUDGE_SYSTEM`. Изменился ответчик: вместо DeepSeek — локальная модель через
  стрим `mlx_lm.server`. Флаг `--json` превращает вывод в события JSONL
  (`retrieve`, `load`, `generate`, `retry`, `judge`, `done`, `error`; в `bench` —
  `start`, `progress`, `summary`).
- `main.js` — Electron. Если на 8080 никто не отвечает, поднимает
  `../w6d1/.venv/bin/mlx_lm.server` и гасит его при выходе; уже запущенный
  сервер использует и не трогает. На каждый вопрос запускает release-бинарник
  дочерним процессом и пересылает события в окно — шарик меняет состояние:
  «ищу» во время поиска, «думаю» во время генерации, тёплый цвет на повторе,
  «проверяю» на судье, спокойный опущенный взгляд на «не знаю».
- `index.html` — интерфейс: дизайн-система Calm Intelligence (`colors_and_type.css`,
  шрифт Manrope из `fonts/`), без внешних CDN.

Отличия ответчика от w5d4, все — из-за локального сервера:

- `response_format: json_object` не передаётся: `mlx_lm.server` 0.32 этого поля не
  читает. Модели оборачивают объект в ```` ```json … ``` ````, поэтому разбор берёт
  текст от первой `{` до последней `}`. Правила проверки цитат не менялись.
- `chat_template_kwargs: {"enable_thinking": false}` уходит для обеих моделей:
  без него Qwen и, как выяснилось на smoke, Gemma 4 E4B сначала размышляют
  сотнями токенов (у Gemma 915 токенов и 34 с до ответа).
- Стрим (`stream: true`) — только ради замеров. В окне ответ появляется целиком.

## Установка

Нужны Rust 1.88+, Node 20+, Python-окружение mlx-lm из w6d1 и скачанные веса:

```bash
# один раз, из w6d1/ — окружение и сервер модели
python3 -m venv .venv && .venv/bin/pip install mlx-lm
# веса обеих моделей (качаются один раз, ~10 ГБ)
.venv/bin/mlx_lm.generate --model mlx-community/Qwen3.5-9B-MLX-4bit --prompt "Привет"
.venv/bin/mlx_lm.generate --model mlx-community/gemma-4-e4b-it-4bit --prompt "Привет"
```

Индекс и кэш эмбеддингов — из w5d1 (`cargo run --release -- index` в `w5d1/`, если их нет).

```bash
# из w6d3/
npm install
npm run package
```

`npm run package` собирает release-бинарник (`cargo build --release`), пишет
`config.json` с путём к папке дня (из Finder и Dock у приложения нет рабочей
папки и PATH терминала), рисует иконку из `icon.svg` и собирает
`release/RagLab-darwin-arm64/RagLab.app`. Его можно перетащить в Applications или
в Dock и запускать двойным кликом. Приложение не подписано; если macOS не даёт
его открыть, открой через контекстное меню «Открыть».
Пути зашиты при сборке — если папку репозитория перенести, пересобери.

Логи: `data/app.log` (что нашло приложение), `data/mlx_server.log` (свой сервер модели).

## Запуск для разработки

```bash
npm start                      # собрать бинарник и открыть окно без упаковки
cargo run --release -- ask "Где узнать, сколько долларов стоил конкретный вызов модели?" --model qwen
cargo run --release -- ask "Какой PIN-код у моей банковской карты?" --model gemma
cargo run --release -- bench                       # 12 вопросов × 2 модели × 3 прогона
cargo run --release -- bench --runs 1 --limit 2    # короткая проверка
```

CLI ждёт уже запущенный `mlx_lm.server` на 8080 (его поднимает приложение или
`w6d1/.venv/bin/mlx_lm.server --model mlx-community/Qwen3.5-9B-MLX-4bit`).
Модель выбирается полем `model` в запросе — сервер перезагружает её сам.
Флаги w5d4 на месте: `--before`, `--after`, `--threshold`, `--index`,
`--retrieval-only`. Вопрос, который начинается с `-`, передавай после `--`:
`ask --model qwen -- "-1 в Kotlin?"`. Команды `check` и `calibrate` из w5d4 убраны: `check`
заменил `bench`, порог не перекалибровывается.

## Метрики сравнения

`bench` сначала один раз ищет фрагменты для всех вопросов (поиск одинаков для
обеих моделей), потом гонит все прогоны на Qwen, затем на Gemma. Перед каждой
моделью — прогревочный запрос в один токен: загрузка весов в замеры не входит
и показывается отдельно. Результат — `data/bench-<дата-время>.json` с сырыми
прогонами и сводкой; вкладка «Сравнение» показывает последний файл.

Вопросы — те же 12, что в `check` w5d4: 10 с ответом в базе и 2 без ответа.
Сводка по каждой модели:

- **Качество.** Доля ответов, где цитаты прошли проверку кодом (ответы ÷
  ответы + провалы после повтора). Доля «подтверждено» у судьи среди
  проверенных (недоступный судья считается отдельно). Верные «не знаю» на
  2 вопросах без ответа. Ложные «не знаю» на 10 вопросах с ответом.
- **Скорость.** Поиск (эмбеддинг вопроса + перебор), мс. Время до первого
  токена. Токены в секунду: токены из `usage` минус первый токен каждой
  попытки, делённые на время после первого токена. Полное время ответа —
  генерация всех попыток, без поиска, загрузки и судьи. Для каждого — p50 и p95
  методом ближайшего ранга.
- **Стабильность.** Валидный JSON-объект с первой попытки. Доля вопросов с
  повтором. Провалы после повтора. Согласованность: во всех N прогонах вопроса
  совпали known/unknown и набор цитируемых чанков (при одном прогоне не
  считается). Ошибки HTTP и сервера — отдельным счётчиком, в доли не входят.

### Smoke 2026-10-07 (2 вопроса, 1 прогон — не результат сравнения)

`bench --runs 1 --limit 2`: Qwen — первый токен ~6,9–7,5 с, ~16 ток/с;
Gemma — ~2,4–2,5 с, ~22 ток/с. Поиск 7–10 мс. На вопросе 1 обе модели
ответили, судья подтвердил. На вопросе 2 Qwen сказал «не знаю», а Gemma не
прошла проверку цитат и после повтора. Отдельный `ask` про стоимость вызова:
Qwen — первый токен 4,1 с, 15,7 ток/с, 10,5 с; Gemma — 1,4 с, 24,6 ток/с,
6,8 с; у обеих цитаты прошли, судья — «подтверждено».

### Полный прогон

Результаты полного `bench` (12 × 2 × 3) заполнит владелец после прогона.

## Ограничения

- Судья — облачная DeepSeek и единственный внешний вызов; офлайн качество
  оценивается только проверкой цитат кодом.
- Порог 0.85 и промпты взяты из w5d4 без подгонки под локальные модели. Они
  писались под DeepSeek, поэтому сравнение показывает, как модели справляются
  с чужим промптом, а не их лучший результат.
- `mlx_lm.server` кэширует префиксы промптов (`cached_tokens` в сырых данных):
  второй и третий прогон того же вопроса могут получить меньшее время до первого
  токена. Сравнение моделей между собой это не искажает — обе в равных условиях.
- Температура — по умолчанию сервера (0, жадная генерация), поэтому
  согласованность прогонов высокая по построению; это стабильность конвейера,
  а не разброс модели.
- Сервер держит одну модель в памяти; переключение занимает от нескольких
  секунд до ~30 с (на smoke 2–29 с, первая загрузка с диска дольше), это видно
  в метрике «загрузка/прогрев».
- Отчёт `bench` переписывается после каждого прогона вопроса: остановленный или
  оборванный прогон остаётся в файле с `"complete": false` (во вкладке — «не завершён»).
  Сбой прогрева модели не обрывает bench: её прогоны записываются как ошибки сервера.

## Проверки

```bash
cargo test
cargo clippy --all-targets -- -D warnings
```

Тесты через локальный HTTP-mock: отбор по порогу и его инварианты; SSE-поток
как у `mlx_lm.server` (keepalive, пустая роль, usage, размышление) и замеры;
снятие ```` ```json ```` и текста вокруг объекта; принятый JSON и сбор
источников кодом; запрос без `response_format` и с `enable_thinking: false`;
повтор с исправлением и с итоговым отказом; «не знаю» без вызова модели;
ошибки сервера и отсутствие сервера; вердикты судьи и «недоступен» без сети
и без ключа; разбор CLI (`--json`, `--model`, `bench --runs --limit`); форма
событий `done` и списка кандидатов; метрики попыток; p50/p95 и сводка `bench`
на фиксированных прогонах с ожиданиями, посчитанными вручную.

## Маршрут для видео

1. Код: `ANSWER_SYSTEM` и `parse_reply` (общие с w5d4), `Local::stream`
   (локальная генерация и замеры), `bench` и `summarize`, `main.js` (сервер
   модели и `HF_HUB_OFFLINE=1`).
2. Клик по иконке-шарику в Dock — окно, в сайдбаре «Сервер модели на связи».
3. Вопрос из подсказок про стоимость вызова: шарик ищет, думает, проверяет;
   ответ, источник, цитата, «подтверждено», метрики. Переключить на Gemma и
   спросить ещё раз — видна загрузка модели.
4. Вопрос про PIN-код — «не знаю» без вызова модели, шарик спокоен.
5. Выключить Wi-Fi: индикатор «Офлайн», вопрос снова получает ответ с цитатами,
   судья — «недоступен (нет сети)».
6. Вкладка «Сравнение» — сохранённый прогон: карточки «Качество / Скорость /
   Стабильность» по моделям и таблица по вопросам.

Не показывай `.env`.
