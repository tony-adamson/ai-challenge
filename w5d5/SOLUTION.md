# День 25: веб-чат и Electron-приложение с RAG и памятью задачи

## Блок 1. Для человека

### Результат

Один веб-чат работает в браузере и как Electron-приложение на macOS, ведёт сохраняемый диалог о будущем агенте, ищет знания в книгах, материалах `g-harness` и источниках прежнего исследователя. Он помнит цель, уточнения, ограничения и термины. После цикла проектирования выдаёт законченный комплект Claude Code-агента и результат пробного запуска. У ответов видны проверяемые источники; отсутствие найденного подтверждения отображается явно. «Готов» означает, что конкретный комплект прошёл согласованные проверки, а не что любой будущий сценарий гарантированно работает.

### Предлагаемое решение

Веб-интерфейс подключается к единственному локальному Node.js API, который хранит состояние, обращается к прежнему API и нужным MCP-инструментам. Electron открывает этот же интерфейс. История, память задачи, источники и результаты проверки видны в одном окне. Локальный поиск использует существующую книжную SQLite-базу и документацию `g-harness`/курса. Для него нужен небольшой Python-helper внутри `w5d5`: установленный Python поддерживает FTS5, а проверенный системный SQLite CLI — нет. Helper только читает источники и возвращает JSON; новый постоянный индекс книг не создаётся. MCP-клиент использует официальный TypeScript SDK. GitHub даёт кандидатов, DeepWiki — дополнительные сведения; ссылки на репозиторий сами по себе не доказывают утверждения о его устройстве. Созданный агент проверяется через установленный Claude Code на тестовых файлах с разрешением только читать их. Каждый режим запускается одной npm-командой и не требует переноса всего старого веб-приложения.

### Границы

В первую версию входят история, RAG на каждом вопросе, источники, память задачи, создание read-only Claude Code-агента, пробная проверка и два длинных сценария. Telegram-бот, универсальный формат экспорта, конвейер Linear/PR, наблюдения по расписанию, уведомления и публикация приложения остаются за пределами задачи. Исходники/данные прежних дней, `books-rag` и `g-harness` сохраняются.

### Размер

Предварительный бюджет после согласованной смены стека: до 14 source-файлов и 1700 строк net production-кода, отдельно до 650 строк поведенческих проверок. Прямые dependencies: runtime MCP client; dev Electron, TypeScript, Node types и Electron packager. Python stdlib уже установлен. Это задача L: браузерный и desktop-режим, локальный API и MCP-клиент вынуждают превысить бюджет обычной M-правки. Копирование 11082 строк старого исследователя отклонено; используем ограниченные UI-паттерны и контракты. Документы и generated lockfiles не входят в LOC source. Точный scope-контракт перед кодом уточнит оценку; превышение вдвое требует остановки.

### Что доказываем

Два сценария по 12–15 пользовательских ходов проходят через тот же chat API/координатор, что и интерфейс. Они проверяют цель, ранние ограничения, явную смену требования, источники, перезапуск и итоговый комплект. Отдельно проверяется созданный агент: он читает тестовые файлы, выполняет предметную задачу, не выдумывает отсутствующие сведения и не следует вредным инструкциям из данных. Отчёт фиксирует реальные наблюдения; ошибки подключения/авторизации не становятся PASS.

### 5. Архитектура и пользовательский цикл

Общий веб-интерфейс показывает список чатов, разговор с источниками, память задачи и комплект/отчёт. Electron создаёт одно основное BrowserWindow с `nodeIntegration:false`, `contextIsolation:true`, `sandbox:true`; renderer не получает Node/API keys и не использует привилегированный preload. Он открывает локальный API origin, как обычный браузер. Фоновые I/O и дочерние процессы не блокируют Node event loop; синхронное сканирование corpus на UI-пути не допускается. «Собрать агента» и «Проверить» используют текущую видимую спецификацию. Сборка может быть явно запрошена в чате; после первого сообщения она не обязательна.

HTTP API: `POST /api/session` — одноразовый обмен bootstrap capability на session cookie; `GET/POST /api/chats`, `GET /api/chats/:id`, `POST /api/chats/:id/ask`, `POST /api/chats/:id/retry`, `POST /api/chats/:id/build`, `POST /api/chats/:id/validate`, `GET /api/chats/:id/operations/:id` для результата/progress, `POST /api/chats/:id/operations/:id/cancel` для отмены и `GET /api/chats/:id/sources/:messageId/:sourceId`, `GET /api/chats/:id/artifacts/:artifactId/files/:fileId`. Read API выдаёт IDs до mutation; отсутствующие chat/message/artifact/source/operation IDs дают 404. Accepted async действия возвращают operationId и status, повтор занятости — 409; malformed input — 400, отсутствующая авторизация — 401. REST handler остаётся тонким вызовом того же координатора, который используют тесты и eval; операции только в памяти, после restart active status восстанавливается по snapshot, без новой persistent queue. Browser и Electron обращаются к одному store/API, оба режима не создают разные copies состояния. Повтор отмены завершённой/отменённой операции возвращает её конечный статус без нового действия; неизвестный operationId — 404. Отмена abort-ит network/helper/Claude subprocess и не публикует частичный ответ.

Координатор хода выполняет последовательно:

1. Сохраняет пользовательское сообщение со статусом memory_pending. Для одного чата одновременно допускается один ход/генерация/проверка; дополнительные действия в UI недоступны до завершения.
2. По пользовательскому сообщению и предыдущей памяти получает структурированный patch памяти и поисковый запрос. Полученные документы не участвуют в обновлении пользовательских решений. Patch принимается только при существующих user-message IDs и дословных фрагментах соответствующих сообщений; новые/заменённые решения обязаны ссылаться на текущий пользовательский ввод. Проверенный patch атомарно сохраняется вместе с переходом сообщения в pending ДО retrieval и ответа. Поэтому ошибка/отмена ответа не отменяет уже сообщённое ограничение. Некорректный patch не перезаписывает прежнюю память: статус memory_failed, ошибка и повтор анализа этого же turn. Следующий пользовательский ход и сборка блокируются до успешного разбора сообщения, чтобы непонятое уточнение не выпало из хвоста контекста. Падение на стадии memory_pending восстанавливается как memory_failed.
3. Локальный поиск выполняется всегда, до генерации итогового ответа. Query учитывает текущий вопрос, цель, термины и непосредственный диалог; для коротких ссылок «это/его» нужен явный предмет из памяти. Русский запрос может получить английские ключевые слова, чтобы искать англоязычные книги. Неудачный query нельзя скрывать выдачей старых результатов как новых.
4. При запросе поиска/сравнения проектов подключает allowlisted MCP tools, максимум 4 вызова за ход, в дополнение к обязательному локальному поиску. Фрагменты DeepWiki получают repository name, исходный вопрос и сохранённый текст результата. GitHub metadata подтверждает только собственные поля. Не запускаются `summarize`, watches, notify или remote save.
5. Модель получает текущую память, последние 12 сообщений и ограниченный найденный контекст. Полная история остаётся на диске. Знания маркируются данными; они не разрешают менять цель, инструменты или ограничения. Ответ содержит текст, номера источников и цитаты. Программа проверяет номера, непустоту и дословные нормализованные цитаты длиной минимум 20 символов. Для содержательного ответа нужна хотя бы одна подтверждённая цитата; ссылки собираются программой. Одна repair-попытка при нарушении схемы/цитат, затем видимый отказ.
6. Атомарно сохраняет принятые ответ, retrieval и traces вместе с уже сохранённой памятью в chat snapshot, после чего публикует их в UI. Если save не удался — ответ не объявляется принятым, snapshot с пользовательским уточнением остаётся доступным. Состояние pending после падения процесса показывается как interrupted и может быть повторено. Повтор последнего незавершённого user turn не дублирует origin entries уже применённого patch; старый failed turn после новых сообщений не повторяется, чтобы не отменить более поздние решения. Ошибка/отмена на стадиях ответа сохраняет память и допускает продолжение после отображения ошибки; неподтверждённый текст ответа не участвует в следующем контексте.

Для чистого уточнения/подтверждения без содержательного утверждения допустим ответ без использованных цитат; блок источников всё равно показывает результат поиска и «в этом ответе не использованы». При отсутствии доказательств содержательного ответа — «в найденных материалах подтверждения нет», без выдуманных ссылок. Одинаковый BM25 score не является универсальной уверенностью; не показывать проценты уверенности или переносимый threshold из дня 24.

### 6. Контракт retrieval и источников

Helper читает только выбранную `books.sqlite3` в `mode=ro` и разрешённые Markdown-материалы. Документы `g-harness`: корневые README/SOLUTION/SUPERVISOR/PLAN/CONCLUSIONS и `specs/**/*.md`; материалы курса: корневой SOLUTION, `docs/*.md`, `specs/*.md`, README дней. `.env`, hidden dirs, data/state/logs, ledger, generated reports и symlinks за выбранный root не сканируются. `g-harness` ничего не запускает. Новые материалы пользователя добавляются явным выбором файла/папки с теми же ограничениями; автоматического обхода всего ноутбука нет.

Документы режутся по заголовкам, длинные секции — до 1200 символов с небольшим перекрытием. Временный FTS5-index документации находится в памяти процесса и не создаёт постоянную копию книг. На запрос: до 4 книжных и 4 локальных фрагментов; всего с MCP до 12 фрагментов и 20000 символов. Ранжирование из разных индексов не смешивается по абсолютному BM25: квоты раздельные. Ограничения input/output helper: максимум 2 MiB на документ, до 500 документационных файлов, до 1 MiB JSON-вывода. Превышение — явная ошибка подключения источника, не молчаливое обрезание смысла.

Каждый найденный фрагмент хранит id, вид источника, название, local path либо URL, section/pages при наличии и точный текст, отправленный модели. Book ID = source + chunk_no; document ID = root-relative source + section + chunk ordinal; номер `[N]` действует только внутри данного хода. Отсутствующие EPUB-страницы не придумываются. Локальный источник открывается по проверенному пути в выбранном root; удалённый — только http(s) ссылкой. Retrieval snapshots сохраняют отправленные фрагменты, поэтому старый ответ можно проверить после изменения исходного документа.

### 7. Память и состояние: схема и происхождение

Постоянный формат — versioned chat JSON с атомарной записью и локальные artifact directories. Ошибка версии/десериализации не заменяет файл пустым. Секреты, весь книжный индекс, вся документация и произвольные удалённые результаты в chat JSON не копируются; сохраняется только ограниченный контекст конкретного хода.

| Поле | Назначение и вынуждающее требование | Источник истины |
|---|---|---|
| chat.schemaVersion | Явное чтение собственного save format, REQ-1 | Код формата |
| chat.id | Изоляция нескольких разговоров, REQ-1 | Создание чата |
| chat.settings | provider/model/temperature/reasoning, REQ-9 | Явный выбор пользователя, как Settings референса |
| messages[].id/role/content | Полная история, REQ-1 | Пользовательский ввод либо принятый ответ |
| messages[].status | memory_pending/memory_failed/pending/accepted/failed/interrupted, REQ-1/2/4 | Координатор и сохранение |
| messages[].retrieval | Фрагменты, ссылки, цитаты, ошибки поиска, REQ-2/3 | Реально выполненный retrieval |
| messages[].replyTo/citations | Assistant ссылается на user turn и использованные цитаты; полный retrieval/traces хранится один раз на user turn, REQ-2/3 | Координатор и проверенные цитаты |
| messages[].toolTraces | Сервер/инструмент/аргументы/ошибка и sourceIds, REQ-10 | Фактические MCP-вызовы; полный текст только в retrieval |
| task.goal | Текущая цель, REQ-4 | Подтверждённый user evidence |
| task.clarifications | Уточнения предметной задачи, REQ-4 | Подтверждённый user evidence |
| task.constraints | Актуальные ограничения, REQ-4 | Подтверждённый user evidence |
| task.terms | Определения терминов, REQ-4 | Подтверждённый user evidence |
| task entries[].messageId/quote | Аудит происхождения и явной смены, REQ-4 | Существующее user message и его подстрока |
| artifacts[].path/specHash | Связь комплекта с актуальной задачей, REQ-7 | Сгенерированный immutable комплект и hash спецификации |
| artifacts[].validation | Адрес единственного отчёта в artifact directory, REQ-8 | Реальный запуск; file hashes/статус/причина находятся в отчёте |

MemoryEntry = `{key: String, value: String, messageId: String, quote: String}`. `goal` — nullable MemoryEntry с фиксированным key `goal`; остальные три контейнера — массивы MemoryEntry с уникальными нормализованными ключами. Сравнение key: trim + lower-case, как `w4d5/src/store.rs:97`. Patch содержит `setGoal`, `upsert(kind, entry)` и `remove(kind, key, messageId, quote)`; все действия имеют user evidence. Upsert заменяет существующий ключ, не добавляя второй актуальный «бюджет». При изменении синонимичного ключа модель обязана адресовать исходный существующий key; конфликт/двусмысленность не принимается как новая независимая запись. Remove отсутствующего ключа — ошибка patch, чтобы не скрывать неверную адресацию. Пустая цель допустима только до постановки/после явной отмены и блокирует сборку. `terms.key` — термин, `value` — определение. История версий уже находится в user messages; новая таблица ревизий не нужна.

`specHash` — SHA-256 канонического JSON `{format:"claude-code-readonly-v1", goal: value-or-null, clarifications:[[key,value]], constraints:[[key,value]], terms:[[key,value]]}`. Ключи нормализованы; массивы сортируются по key; строки value — Unicode NFC с нормализованными переводами строк и trim, без изменения внутреннего смысла. Отдельные JSON object keys имеют фиксированный порядок; encoding UTF-8. messageId/quote, история, retrieval, provider/model и статусы в specHash не входят: это provenance/исполнение, а не назначение агента. Уточнения в памяти только предметные, обычный разговор туда не сохраняется. Исправление предметного value меняет hash; новая ссылка evidence на тот же value — нет. File hashes относятся к точным bytes комплекта, включают агента, README, test fixtures и критерии; это отдельная проверка изменённых файлов. Отчёт также хранит specHash, что позволяет сравнить его с актуальной памятью.

Нет долгосрочной общей памяти, дублированной state machine, отдельного счётчика ревизий или сохранённых derived badges. Отображаемый статус готовности вычисляется по текущему specHash, существующему отчёту и проверенным file hashes. Поправка пользователя заменяет актуальное решение; предыдущая версия остаётся в исходной истории. Обнаруженное противоречие без явного выбора обсуждается в чате и блокирует финальную сборку.

### 8. Комплект агента и проверка

Комплект содержит `.claude/agents/<name>.md`, `README.md` с назначением/ограничениями/запуском/источниками и предметный набор тестовых файлов/критериев. Frontmatter задаёт name, description, tools — только подмножество Read/Grep/Glob — и `model: inherit`. Имя проверяется кодом; пути задаёт приложение, модель не выбирает абсолютные пути. Не допускаются TODO, placeholder-секции, неразрешённые tools, hooks, MCP configs, память с записью или предложение ручного дописывания обязательной функции. Требование вне read-only границы означает уточнение scope, а не выпуск ложного «готово».

Статическая проверка проверяет контракт файла и покрытие текущих требований. Предметные критерии согласуются в диалоге до сборки; ожидаемые факты берутся из тестовых файлов/требований, а не из ответа проверяемого агента. Критерии включают фактическую задачу, неизвестный факт и инструкцию внутри данных, конфликтующую с правилами агента. Для критериев с неоднозначной смысловой оценкой автоматический judge — дополнительное свидетельство; требуется ручная сверка, такая оценка одна не даёт PASS.

Пробный запуск использует Node `spawn` с argv и `shell:false`: установленный `claude --print`, тот же parsed agent body/frontmatter через `--agents` и `--agent`, `--restricted`, `--tools Read,Grep,Glob`, `--permission-mode dontAsk`, `--strict-mcp-config` с пустым config, отключённые hooks и `--no-session-persistence`. CWD — новый test directory; symlinks не разрешены. `--restricted` в проверенном локальном help ограничивает file tools рабочими директориями и игнорирует user/project/local settings. `--bare` не используется: официальный контракт отключает OAuth, а пользователь выбрал пробный запуск через установленный Claude Code. Модель Claude не переопределяется приложением; фактическая модель записывается в отчёт.

Лимиты: до 3 предметных запусков на комплект, до 180 секунд на каждый, stdout/stderr до 1 MiB, корректное чтение обоих pipe без deadlock. Отмена/таймаут завершает дочерний процесс и не получает PASS. JSON/stream-json result анализируется по success/error и tool events; exit 0 сам по себе недостаточен. До/после сравниваются hashes тестовых файлов; любые изменения дают FAIL. Проверка возможностей CLI обязательна: отсутствие `--restricted` блокирует run без небезопасного fallback.

Комплект создаётся в новом version-directory внутри пользовательской output root; старый не перезаписывается. Проверка относится к точным hashes файлов и текущей спецификации. Статусы: собран/не проверен, проверка пройдена, проверка провалена, проверка недоступна, устарел. «Готов» показывается только для прошедшего комплектa, совпадающего с текущей задачей. Полный тестовый отчёт содержит ответы, инструменты, критерии, исходные ожидания и честные ограничения области проверки. Установка в глобальную `~/.claude/agents` не выполняется автоматически.

### 9. Ошибки, сроки и безопасность

HTTP API timeout 60 секунд; MCP connection/call 20 секунд; local helper 15 секунд. Повтор ответа только по ошибке схемы/цитат — максимум один. API/MCP/CLI-ошибки не повторяются бесконечно и показываются отдельно. MCP недоступен — локальный RAG продолжается с явной пометкой; ответ, зависящий от отсутствующего внешнего источника, не подменяется знанием модели. Все локальные источники недоступны — содержательный ответ не генерируется до восстановления поиска. Нет поддержанных цитат — честное отсутствие подтверждения. Отмена не публикует частичный результат как принятый.

Локальный API слушает только 127.0.0.1 на свободном порту, не публикуется в LAN/VPS. TOTP старого сервиса заменён локальной capability-сессией для нового браузерного интерфейса (REQ-6 Amendment); старый сервис не изменяется. Ключи читаются из явно выбранной корневой `.env`, не из shell sourcing; имена ключей сохраняются. Provider/model/temperature/reasoning задаются и сохраняются в chat.settings, а не берутся из LLM_PROVIDER/LLM_MODEL дня 24. При первом запуске до первого модельного вызова пользователь явно выбирает настройки из прежних API, без автоматической подстановки другой модели. Chat Completions сохраняет provider-specific wire semantics: Cerebras `max_completion_tokens` и `reasoning_effort`; DeepSeek `max_tokens`, `thinking`, при включении `reasoning_effort`; OpenRouter `max_tokens` и отключённый context-compression plugin, как `w4d5/src/agent.rs:864`. Для структурированных стадий `stream:false` и JSON response_format; UI показывает progress стадий вместо токенового стрима. Токеновый стрим, метрики стоимости и каталог цен не являются требованиями дня 25; отказ API от выбранного параметра виден и не вызывает молчаливой смены модели/режима. Внешнему API передаются текущая задача, хвост диалога и ограниченные найденные фрагменты, не целые книги/репозитории. Состояние, тестовые fixtures и output roots отделены от источников. Источники не считаются инструкциями. Создание внешних отчётов, cloud write и VPS deploy не выполняются автоматически. Старый `research.search_repositories` сохраняет результаты в своей серверной SQLite и выдаёт search_id (`w4d5/src/watch.rs:458`); это существующая побочная запись retrieval, а не эфемерный read-only поиск. Никаких дополнительных инструментов записи приложение не вызывает.

### 10. Семантика действий и lifecycle

Локальная сессия: запуск/кнопка «Открыть в браузере» создаёт случайную 256-bit capability со сроком 60 секунд, используемую ровно один раз. Она передаётся frontend через URL fragment, удаляется из адреса сразу после чтения и POST-обмена на случайную HttpOnly SameSite=Strict session-cookie. Capability/cookie не попадают в логи, отчёты или persistent state. Browser-mode стартует штатный браузер с этим URL, консоль печатает только адрес без fragment. Session и незавершённые bootstrap capabilities существуют только в памяти сервера до shutdown. HTTP listener задаёт точный Host; Origin, если есть, должен совпадать с локальным origin; cross-site fetch отвергается, CORS для сторонних origins отсутствует. Все /api, включая чтение файлов/источников, требуют сессию, кроме bootstrap с проверкой capability. POST принимает JSON и ограниченный body; ошибка capability — 401, чужой Origin/Host — 403. API endpoints не принимают произвольный путь от модели/frontend: sourceId/fileId разрешается через принадлежащий chat snapshot и выбранные roots. Источники и artifact files API возвращает только JSON-полями; UI показывает их через textContent. Скачивание выдаётся как attachment с application/octet-stream и X-Content-Type-Options: nosniff. Исполняемые frontend-ресурсы обслуживаются только по фиксированному allowlist; HTML/SVG/JS fixture не становится ресурсом origin. Content-Security-Policy запрещает inline scripts/remote code; тексты модели и источников рендерятся через textContent без сырого HTML. Electron запрещает навигацию окна на другой origin и создание произвольных окон; проверенные внешние http(s) ссылки открываются штатным браузером.

В каждом режиме один сервер на запущенный экземпляр приложения. Второй экземпляр на том же data root не допускается: эксклюзивный локальный lockfile с PID, проверкой живого владельца, безопасным снятием stale lock и удалением на shutdown. Lockfile — служебная координация одного writer REQ-1, не очередь/сервис. Закрытие Electron завершает его server и дочерние процессы; standalone browser-mode завершает их по SIGINT/SIGTERM. Сервер не завершает процессы другого экземпляра. Наличие открытой браузерной вкладки после shutdown отображается как потеря соединения; состояние сохраняется до shutdown. Настройки и store общие для обоих интерфейсов.

| Действие | Условия | Результат | Повтор/ошибка/конкурентность |
|---|---|---|---|
| Создать чат | Локальный пользователь | Новый пустой snapshot | Новый id; ошибка записи видна |
| Отправить вопрос | Настроенный API, чат свободен, нет memory_failed | Один сохранённый user turn; его проверенная память сохраняется до ответа, затем accepted answer/retrieval либо failure | Повтор использует тот же turn без дублирования origin; memory_failed требует успешного повтора до следующего хода; один активный процесс на чат |
| Собрать | Нет незакрытого противоречия, задача read-only сформулирована | Новый законченный комплект, первоначально не проверен | Ошибка не удаляет старый комплект; повтор создаёт новую версию |
| Проверить | CLI capability check и auth доступны, immutable комплект | Привязанный к hashes отчёт | Без auth — unavailable; повтор обновляет отчёт конкретного комплекта, не сам агент |
| Продолжить после перезапуска | Читаемый snapshot | История и прежняя память восстановлены | pending становится interrupted, memory_pending — memory_failed; без автоматического внешнего вызова |
| Изменить цель/ограничение | Новый user evidence | Актуальная память; прошлый комплект может стать устаревшим | Старые файлы и история сохранены |

Чаты создаются/обновляются только координатором; старые данные не мигрируются. Удаление чатов/артефактов из UI в первую версию не входит. Temporary test directory удаляется только внутри собственного app temp root после завершения; отчёт и комплект сохраняются. Информация об источниках относится к тому snapshot retrieval, на котором сформирован ответ; исходные книги/репозитории не меняются. Пересборка базы не является операцией приложения.

В обоих проверяются ранняя цель, 2–3 ограничения, термин, смена одного требования, короткий вопрос со ссылкой на прежний предмет, перезапуск и финальная сборка/проверка. Видео показывает пользовательский поток, источники, память, итоговые файлы и отчёт без секретов. Саму запись видео пользователь выполняет по подготовленному сценарию, если отдельно не поручит записать экран.

Официальные внешние контракты: [TypeScript MCP SDK](https://github.com/modelcontextprotocol/typescript-sdk), [Claude Code agents](https://code.claude.com/docs/en/sub-agents), [программный запуск](https://code.claude.com/docs/en/headless), [hooks](https://code.claude.com/docs/en/hooks). Restricted mode дополнительно подтверждён локальным `claude --help` версии 2.1.288. `--settings` с `disableAllHooks:true` отключает пользовательские/project/plugin hooks; managed hooks могут сохраняться. До проверки агента preflight проверяет наличие managed policy hooks без вывода их содержимого: если их нельзя отключить, запуск помечается unavailable, без обещания полной изоляции. Источник capability-failure отображается пользователю; глобальные настройки не меняются.

Эти факты неизвестны до реализации/preflight; они не являются принятыми пользовательскими допущениями. Архитектура согласована пользователем. PlanF3 не выбирает заново источник памяти, способ retrieval, формат комплекта, инструменты проверки или критерий готовности. Budget и non-goals обязательны.
