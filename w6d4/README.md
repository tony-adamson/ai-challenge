# w6d4 — Книжный исследователь: локальная модель, оптимизированная под задачу

День 29: оптимизировать локальную LLM под конкретный кейс и сравнить до/после.
Кейс — агент с tool calling по моим книгам об ИИ-агентах и LLM (`~/MyProjects/books-rag`,
раздел «ИИ и машинное обучение/Агенты и LLM», 11 книг, 1435 фрагментов, FTS5).
Агент сам ищет, читает фрагменты и отвечает с цитатами; дословность цитат проверяет код.

Модель — `mlx-community/Qwen3.5-9B-MLX-4bit` через `mlx_lm.server` (веса уже 4-битные).
Оптимизация — один профиль против другого на тех же весах:

| Параметр | До (`baseline`) | После (`optimized`) |
|---|---|---|
| Сэмплинг | из карточки модели: temperature 0.7, top_p 0.8, top_k 20 | temperature 0 (жадно) |
| max_tokens | 1200 | 400 |
| Контекст: фрагментов на поиск | 5 | 3 |
| Контекст: текст фрагмента | целиком (~460 слов) | окно 180 слов вокруг слов запроса |
| Промпт | общий: «ты полезный ассистент, вот формат» | под кейс: FTS5 ищет по словам, запрос 2–5 слов, книги EN+RU — повтори на другом языке, ≤ 3 поисков, цитата 20–200 символов дословно, «нет данных» |
| Квантование | веса 4 бит, KV-кэш 16 бит | веса 4 бит, KV-кэш 8 бит с 0-го токена (`--kv-bits 8 --quantized-kv-start 0`) |

Общие для обоих: `enable_thinking: false`, `seed` 42, до 4 вызовов инструментов на вопрос,
одинаковые инструменты и одинаковый формат финального ответа (JSON с `known`, `answer`, `quotes[{id, text}]`) —
иначе качество не сравнить.

«Context window» здесь — сколько текста агент кладёт в окно: `mlx_lm.server` 0.32 не принимает
ограничение окна в запросе (`max_kv_size` есть только у `mlx_lm.generate`), поэтому окно режется на стороне
инструмента: меньше фрагментов и обрезка до окна. Веса заново не квантовались — без докачки в кэше есть
только 4-битные; квантование, которое пробуем, — KV-кэша.

## Что измеряется

Вопросы — 14 эталонов `books-rag/evals/agents-llm-questions.md` в `questions.json`: 13 с ответом
(ожидаемая книга, иногда одна из двух), E14 — ловушка (Kubernetes/Helm), верный ответ — «нет данных».
Судьи нет: всё проверяется кодом, офлайн.

- **Качество.** Ожидаемая книга процитирована (цитата с `id` фрагмента, который агенту выдал инструмент,
  и книга из эталона). «Нет данных» на E14 (`known: false`). Цитаты дословно есть в полном тексте фрагмента
  (пробелы и регистр не важны, не короче 20 символов). Ответ в формате JSON. Число поисков.
- **Скорость.** Первый токен финального ответа — в него входит чтение всего накопленного контекста.
  Скорость генерации финального ответа, ток/с (раунды с вызовом инструмента сервер не стримит:
  `tool_calls` приходят одной дельтой в конце). Полное время вопроса со всеми раундами. Медианы.
- **Ресурсы.** Prompt-токены за вопрос (сумма по раундам, из `usage`). Пиковая память `mlx_lm.server` —
  `phys_footprint_peak` из `footprint`: RSS из `ps` у MLX показывает ~250 МБ, потому что веса и KV-кэш
  лежат в памяти GPU (IOAccelerator) и в RSS не входят. Пик берётся за жизнь процесса; `bench.sh`
  перезапускает сервер на каждый профиль, поэтому пик — свой у каждого.

## Как устроено

- `src/main.rs` — агент на Rust. Поиск по индексу books-rag (абсолютный путь, только чтение; логика как в
  `books_kb.py`: сначала все слова, потом любое, BM25), инструменты `search_books(query, limit?)` и
  `read_chunk(id)`, цикл tool calling через стрим `mlx_lm.server`, проверка ответа кодом, `bench`.
  Модель и флаг `--kv-bits` бинарник читает из командной строки процесса на 8080 (`lsof` + `ps`):
  профиль `optimized` на сервере без KV-квантования — понятная ошибка, а не тихо неверный замер.
- `scripts/bench.sh` — бенч до/после одной командой: сервер baseline → `bench` → сервер с KV 8 бит → `bench`.
  Порт 8080 занят — выходит с сообщением, чужие процессы не трогает. Отчёты — `data/bench-<профиль>-<модель>-<время>.json`.
- `main.js` — Electron. Поднимает свой `mlx_lm.server` с флагами профиля; переключатель профиля
  перезапускает только свой сервер (чужой на 8080 не трогает и говорит об этом). Всё с `HF_HUB_OFFLINE=1`.
- `index.html` — окно: вкладка «Вопрос» (шаги агента, ответ, цитаты с отметкой дословности, эталон,
  метрики) и «Сравнение» (параметры, до/после по качеству, скорости и памяти, таблица по вопросам из
  последних отчётов `bench`).

Находка по ходу: если после лимита вызовов слать запрос без `tools` (как в w4d5), шаблон чата меняет
системную часть промпта, кэш префикса сервера промахивается, и Qwen перечитывает весь контекст заново —
на smoke это +110 с на один вопрос. Поэтому `tools` уходят в каждом запросе, а лишние вызовы получают
ответ «лимит».

## Установка

Нужны Rust 1.88+, Node 20+, окружение mlx-lm из w6d1 и веса в кэше Hugging Face (по README w6d1),
индекс books-rag (`python3 scripts/books_kb.py build` в `~/MyProjects/books-rag`).

```bash
# из w6d4/
npm install
npm run package     # release-бинарник + release/BookResearcher-darwin-arm64/BookResearcher.app
```

Приложение не подписано; если macOS не даёт открыть — контекстное меню «Открыть».
Пути зашиты при сборке (`config.json`) — если папку перенести, пересобери.
Логи: `data/app.log`, `data/mlx_server.log`.

## Запуск

```bash
npm start                                     # окно без упаковки
sh scripts/bench.sh                           # полный бенч: 14 вопросов × 2 профиля
sh scripts/bench.sh --limit 3                 # короткая проверка
sh scripts/bench.sh --model gemma --limit 3   # то же на Gemma 4 E4B
```

CLI ждёт уже запущенный сервер на 8080 (его поднимают приложение и `bench.sh`):

```bash
cargo run --release -- ask --profile optimized -- "Чем ReAct-агент отличается от одношагового агента?"
cargo run --release -- bench --profile baseline --limit 3
```

- E2 провалили все: Qwen «до» упёрся в лимит раундов, вызывая `read_chunk` по кругу, и не дал ответа;
  Qwen «после» процитировал claude-code-for-dx вместо гайда по Skills; Gemma «до» не вернула JSON.
- Ловушка E14 отдельным `ask`: Qwen «до» — «нет данных» за 88 с и 23,7 тыс. prompt-токенов, «после» — за 39 с и 8,3 тыс.
- Живой вопрос из окна (E6, «после»): книга совпала, 3/3 цитаты дословно, 61 с, 5,9 тыс. prompt-токенов, пик 6,9 ГБ.

**Почему Qwen, а не Gemma.** Gemma 4 E4B быстрее и легче, но профиль «после» на ней не запускается:
у Gemma 4 часть слоёв со скользящим окном (`RotatingKVCache`), и `mlx_lm` 0.32 на `--kv-bits` падает с
`NotImplementedError: RotatingKVCache Quantization NYI` — сервер рвёт поток, ответа нет. Квантование KV-кэша —
часть задания, поэтому модель дня — Qwen3.5-9B. Tool calling работает у обеих (`tool_calls`, `finish_reason: tool_calls`).

### Полный прогон

Не запускался: `sh scripts/bench.sh` (14 вопросов × 2 профиля) по оценке из smoke идёт около часа —
«до» ~2,5–3 мин на вопрос (~40 мин), «после» ~1–1,5 мин (~20 мин). Сравнение до/после выше — по 3 вопросам.

## Ограничения

- Один прогон на вопрос. У baseline сэмплинг случайный (seed фиксирован, но сервер перезапускается),
  поэтому отдельные вопросы могут меняться от прогона к прогону; сравнение — по 14 вопросам целиком.
- Качество без судьи: книга и дословность цитаты проверяются кодом, а то, отвечает ли текст на вопрос, — нет.
- KV-кэш 8 бит на контексте в несколько тысяч токенов экономит мало: память сервера в основном — веса.
  Основной выигрыш в памяти и скорости даёт меньший контекст.
- Окно 180 слов вокруг слов запроса может отрезать нужное место; для этого у агента есть `read_chunk`.
- `mlx_lm.server` держит одну модель; смена профиля в окне — перезапуск сервера, 10–30 с.
