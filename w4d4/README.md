# Исследователь — наблюдения по расписанию и сводка в Telegram

День 18: MCP-инструмент с периодическим выполнением. Собственный MCP-сервер
наблюдает за поиском GitHub по расписанию, хранит снимки в SQLite и отдаёт
агрегированную сводку. Приложение раз в N минут собирает сводку по всем
наблюдениям, DeepSeek пишет дайджест, и он уходит в Telegram. Основа — `w4d2`:
чат, память, инварианты, этапы и утверждение плана сохранены.

Один бинарник, два режима:

- `--mcp-server` — MCP по Streamable HTTP на `127.0.0.1:8800/mcp` и планировщик
  снимков в том же процессе. Наружу не публикуется, токена нет: слушает только localhost.
- без аргументов — веб-интерфейс с агентом на `127.0.0.1:8799`, вход по TOTP,
  фоновый цикл сводок. К MCP-серверу подключается как клиент по `WATCH_MCP_URL`.

## Инструменты MCP-сервера

- `search_repositories(query, limit)` — поиск GitHub, как в `w4d2` (limit 1–5).
- `watch_create(query, every_minutes)` — наблюдение за поисковым запросом;
  интервал — целое число от 1 до 1440 минут, query — непустая строка до 256 символов.
  Наблюдений не больше 5 (лимит поиска GitHub без токена), шестое — ошибка.
- `watch_list` — наблюдения: id, запрос, интервал, время создания и последнего
  запуска, статус последнего запуска, число снимков.
- `watch_delete(id)` — удалить наблюдение вместе со снимками.
- `watch_summary(id, since)` — сводка от `since` (RFC3339; по умолчанию — время
  создания) до последнего снимка: новые репозитории, топ прироста звёзд, свежие
  push (после `since`), число успешных и неудачных запусков, время первого
  и последнего снимка. База сравнения — последний снимок не позже `since`,
  если его нет — первый снимок.

Ошибка возвращается результатом с `isError: true`, а не пустым успехом.

Планировщик раз в 20 секунд запускает наблюдения, у которых подошло время,
по очереди: у поиска GitHub без токена лимит 10 запросов в минуту. Пропущенное
за время простоя запускается один раз, без догоняющей очереди. Каждый запуск —
запрос к GitHub на 30 репозиториев и снимок в `data/watch.db`
(`WATCH_DB` переопределяет путь). Запуски старше 7 дней вместе со снимками
удаляются на каждом тике. Ошибка GitHub пишется в базу как запуск со
статусом `error` и не останавливает планировщик. Схема создаётся при старте.

## Цикл сводок

Каждые `SUMMARY_EVERY_MINUTES` минут (по умолчанию 60) приложение через MCP
вызывает `watch_list` и `watch_summary` по каждому наблюдению с `since` = время
последнего снимка, попавшего в прошлую сводку. Если есть изменения, DeepSeek пишет
один дайджест (провайдер DeepSeek независимо от выбранного в чате); если нет —
короткое «без изменений» со временем последнего снимка. Текст уходит в Telegram
через `sendMessage`, длиннее 4096 символов обрезается. Наблюдений нет — ничего не
отправляется. Без `TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID` отправка пропускается
с сообщением в stderr. Ошибки LLM и Telegram попадают в лог и в статус; период
сдвигается только после успешной отправки. Последний дайджест и время — в
`data/summary_state.json`, их показывает вкладка **Наблюдения** в панели «Контекст».

## Запуск локально

Rust 1.88 или новее. Команды — из папки `w4d3`. Ключи — в корневом `.env`
(шаблон `../.env.example`).

1. Секрет для входа:

   ```bash
   cargo run -- --totp-init
   ```

   Строку `TOTP_SECRET=…` добавить в корневой `.env`, otpauth-ссылку — в приложение-аутентификатор.
2. Терминал 1 — MCP-сервер с планировщиком:

   ```bash
   cargo run -- --mcp-server
   ```

3. Терминал 2 — веб-интерфейс:

   ```bash
   cargo run
   ```

   Открыть `http://127.0.0.1:8799`, ввести код из приложения. Без `TOTP_SECRET`
   веб-режим не стартует. Cookie сессии `Secure`: браузеры принимают её на
   `http://localhost`/`127.0.0.1`, отдельного режима без входа нет.

Дополнительно:

```bash
cargo run -- --github-tools                     # каталог MCP-сервера наблюдений
cargo run -- --github-search 'mcp language:Rust' # один поиск через MCP-сервер
cargo run -- --summary-now                      # один прогон цикла сводок и выход
```

Эти команды ходят в запущенный `--mcp-server`. Вход: 5 неверных кодов за минуту или 20 за час —
дальше 429, пока ошибки не выйдут из окна. Сессия живёт 30 дней и переживает перезапуск
(`data/sessions.json`). Выход — кнопка «Выйти» в сайдбаре (POST /logout).

## Telegram

1. Создать бота у @BotFather, токен — в `TELEGRAM_BOT_TOKEN`.
2. Написать боту любое сообщение.
3. Узнать chat_id:

   ```bash
   curl -s "https://api.telegram.org/bot<TOKEN>/getUpdates" | grep -o '"chat":{"id":-\?[0-9]*'
   ```

   Число — в `TELEGRAM_CHAT_ID`. Для демо удобно `SUMMARY_EVERY_MINUTES=10`.

## Деплой

Файлы в `deploy/`: `Caddyfile` (challenge.hoapps.dev → 127.0.0.1:8799),
`w4d3-mcp.service`, `w4d3-web.service` (веб стартует после MCP) и `deploy.sh`.
Скрипт копирует исходники `w4d3` и `.env.example` на `personal-ru` в
`~/ai_challenge/`, собирает release на сервере и перезапускает обе службы.
`.env` скрипт не копирует: `~/ai_challenge/.env` на сервере создаётся руками
(`DEEPSEEK_API_KEY`, `TOTP_SECRET`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`,
`SUMMARY_EVERY_MINUTES`). Данные чатов на сервере начинаются с нуля.

## Где смотреть код

- `src/watch.rs` — MCP-сервер: инструменты, SQLite, планировщик, агрегация сводки.
- `src/github.rs` — запросы к GitHub Search API.
- `src/summary.rs` — цикл сводок, состояние, отправка в Telegram.
- `src/auth.rs`, `static/login.html` — TOTP, сессии, middleware, ограничение попыток.
- `src/mcp.rs` — HTTP-клиент MCP; `src/agent.rs` — каталог → tool call → результат, дайджест DeepSeek.
- `static/index.html` — вкладка «Наблюдения» и кнопка выхода.

Инструменты модели доступны на тех же условиях, что в `w4d2`: на этапе
**Выполнение** после утверждения плана, один вызов инструмента за ход.
Модели передаётся весь каталог сервера наблюдений.

## Проверки

```bash
cargo test
cargo clippy --all-targets -- -D warnings -A clippy::too_many_arguments -A clippy::double_ended_iterator_last
cargo build --release
```

102 теста прошли. Новые тесты: MCP-клиент приложения ↔ Streamable HTTP сервер
SDK по настоящему HTTP, GitHub заменён локальным fixture (каталог из 5
инструментов, неверные параметры не доходят до GitHub, запуск планировщика,
список, сводка, удаление); сводка на фиксированных снимках в SQLite in-memory
(новые, прирост звёзд, свежие push, запуски, since с часовым поясом, неверный
since); вход через HTTP с кодами из тестовых векторов RFC 6238 (401 для API,
редирект страниц, cookie с HttpOnly/Secure/SameSite, допуск ±1 шаг, запрет
повтора кода, 429 после пяти ошибок за минуту и двадцати за час, сессия после перезапуска, выход);
отправка в Telegram на локальный fixture (обрезка до 4096, ошибка без токена в тексте).

## Сценарий видео

1. Показать в `src/watch.rs` инструменты, схему SQLite и планировщик.
2. Открыть https://challenge.hoapps.dev, войти кодом из приложения-аутентификатора.
3. В новом чате: «Заведи наблюдение за GitHub-поиском `mcp server language:Rust`
   с интервалом 3 минуты. Сначала предложи короткий план». Утвердить план,
   попросить выполнить. Показать карточку `watch_create`.
4. Открыть панель «Контекст» → «Наблюдения»: запрос, интервал, число снимков растёт.
5. Попросить агента: «Покажи сводку по наблюдению» — карточка `watch_summary`.
6. Через 10 минут показать сообщение в Telegram и тот же дайджест во вкладке «Наблюдения».
